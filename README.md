## Особенности проекта и модель данных

Проект имитирует аналитику для магазина товаров для животных с дополнительным благотворительным модулем (донаты и покупка charity-товаров). Важно: данные не берутся из готового датасета — **они генерируются в реальном времени** и проходят полный E2E-пайплайн (Kafka → Vector → Elasticsearch → UI).

### 1) Генерация поведения пользователей (user journey)

Сервис `generator` постоянно создаёт поток событий, который похож на реальное поведение людей в интернет‑магазине:

- Пользователь заходит на сайт и **смотрит товар** (`product_viewed`)
- Часть пользователей добавляет товар в корзину (`add_to_cart`)
- Иногда применяет купон на скидку (`coupon_applied`)
- Часто выбирает тип доставки (`delivery_selected`)
- Иногда завершает оформление (`checkout_completed`) — при этом платеж может быть `paid` или `failed`
- В небольшом проценте случаев после успешной оплаты происходит **возврат** (`order_refunded`)
- Параллельно часть пользователей делает **донаты** (`donation_created`)
- И отдельно моделируется покупка “благотворительного товара” (например мешок корма для приюта) (`charity_item_purchased`)

То есть генерируются **цепочки событий с логикой и вероятностями**: просмотр → корзина → покупка (+ купон/доставка) → (иногда) возврат.

---

### 2) Реалистичное распределение пользователей и событий

В генераторе используются приёмы, делающие поток событий “не игрушечным”:

- `user_id` берётся не равномерно, а по распределению с “хвостом” (Pareto):
  - много обычных пользователей
  - немного “суперактивных”, которые генерируют больше действий
- `session_id` связывает цепочку событий в рамках одной сессии пользователя
- `request_id` позволяет имитировать трассировку запросов
- Время событий — реальное (`ts` в ISO-формате UTC), затем приводится к `@timestamp`

---

### 3) Сценарии нагрузки (поведение системы можно переключать)

Генератор поддерживает сценарии (env `SCENARIO`), чтобы можно было демонстрировать разные режимы работы аналитики:

- `normal` — обычная активность
- `spike` — периодические всплески RPS (нагрузочные пики)
- `payment_outage` — деградация платежей: больше `failed` (важно для метрик fail-rate)
- `promo_day` — “день акции”: повышенная конверсия и активнее использование купонов

Это помогает показать, что UI и агрегации действительно реагируют на изменения входного потока.

---

### 4) Какие данные есть в событиях (поля)

Каждое событие — JSON-документ. Общие поля (почти во всех событиях):

- `ts` → преобразуется в `@timestamp` (Vector)
- `event_name` — тип события (см. список ниже)
- `event_version` — версия схемы события (например `1.1`)
- `service`, `env` — источник событий и окружение
- `scenario` — активный сценарий генерации
- `user_id`, `session_id`, `request_id`
- гео/контекст:
  - `country`, `city`
  - `device` (`mobile|desktop`)
  - `source` (`web|android|ios`)

Поля для e-commerce части:
- товар:
  - `product_id`, `product_name`
  - `category` (food/toys/accessories/hygiene)
  - `pet_type` (cat/dog/mixed)
  - `product_price`, `quantity`
- купоны/скидки:
  - `coupon_code`, `discount_pct`, `discount_amount`
- доставка:
  - `delivery_type` (courier/pickup)
  - `delivery_price`
- заказ/платёж:
  - `order_id`
  - `payment_status` (`paid|failed`)
  - `gross` (сумма без скидок/доставки)
  - `revenue` (выручка; 0 если платёж failed)
  - `currency`
- возвраты:
  - `refund_id`, `refund_reason`, `refund_amount`

Поля для благотворительности:
- донаты:
  - `donation_id`
  - `campaign_id`, `campaign_name`, `cause`
  - `amount`, `donation_status` (`success|failed`)
- charity-товары:
  - `campaign_*`
  - `payment_status`, `revenue`
  - товар из списка charity items

---

### 5) Список event types (что реально летит в Kafka)

- `product_viewed` — просмотр товара
- `add_to_cart` — добавление в корзину
- `coupon_applied` — применение купона
- `delivery_selected` — выбор доставки
- `checkout_completed` — завершение checkout (paid/failed)
- `order_refunded` — возврат по заказу (только для paid)
- `donation_created` — донат (success/failed)
- `charity_item_purchased` — покупка благотворительного товара (paid/failed)

---

### 6) Нормализация и “подготовка к аналитике” (Vector)

Vector делает проект ближе к production, потому что данные не просто “переливаются”:

- поле `ts` превращается в `@timestamp` (стандарт для аналитики)
- числовые значения приводятся к правильным типам (`int/float`), чтобы работали суммы/агрегации
- добавляется признак `is_charity` (донат или charity-item)
- данные индексируются в Elasticsearch с daily-индексами:
  - `pawfund-events-YYYY.MM.DD`

---

### 7) Какие метрики считает UI (и почему они осмысленные)

`web-ui` (FastAPI) строит метрики напрямую из Elasticsearch, без промежуточных BI-инструментов:

Dashboard (`/`):
- общий поток событий
- события по типам
- `views`, `add_to_cart`, `paid orders`
- **add_to_cart_rate** и **conversion**
- выручка магазина (`revenue_shop`)
- AOV (average order value)
- сумма возвратов и net revenue (`revenue - refunds`)
- fail-rate платежей
- сумма успешных донатов
- revenue по charity-items
- график events/minute (видно spikes)

Funnel (`/funnel`):
- просмотры → корзина → оплаченные заказы
- доля возвратов от paid

Top (`/analytics`):
- топ товаров, типов питомцев
- топ благотворительных кампаний
- популярные купоны и варианты доставки

Events (`/events`):
- просмотр “сырых” событий (последние 200) для отладки пайплайна

---

### 8) Почему это E2E, а не “просто сервисы в compose”

Поток данных реально проходит весь цикл:
1. Генерация событий как пользовательского поведения
2. Доставка в Kafka
3. Чтение из Kafka и обработка в Vector
4. Индексация в Elasticsearch
5. Агрегации + визуализация через отдельный web-сервис

То есть можно наблюдать, как изменения сценария (`spike`, `payment_outage`, `promo_day`) отражаются в метриках и графиках практически в real-time.
